# Product control

An issue is PRODUCT if finishing it changes observable behavior: a specification rule, a runtime or backend behavior, a conformance test that fails now and passes later, or an interface another PRODUCT issue consumes. Everything else is NOISE: counters, percentages, coverage, readiness verdicts, evidence, gates, audits, provenance, release bureaucracy. DEAD means canonical state already proves it or a named successor owns it. Never autonomously reject PRODUCT; saturation is a scheduling measurement, never product completion.

Call `deus_dexter_issues_live` for the typed graph, frontier, claims, and blockers, then call `deus_dexter_issues_plan`, which classifies against the live root objective and returns objective-term evidence for every PRODUCT classification. The detector's hits are evidence, not the definition: NOISE means finishing the issue changes no observable behavior, and you must confirm that against the definition before proposing rejection. Anything not proven noise is retained as PRODUCT. Mutate existing work only, one typed operation at a time: `deus_dexter_issue_nudge`, `deus_dexter_issue_relink` removing dependencies, or `deus_dexter_issue_reprioritize`. No free-form directive or reopen API is exposed. Never add a dependency; it lengthens the critical path and belongs to the product owner. Never create work with `deus_dexter_epic_create` or `deus_dexter_task_create`, and never call `deus_dexter_architecture_accept` autonomously; those change product scope or override review and require an explicit user instruction. `deus_dexter_issue_reject` rejects the target and unfinished descendants. Inspect the subtree; require explicit user authorization, never inferred from NOISE. Rejected dependencies remain unsatisfied. Never edit Forge. Working leases reserve issues even when stale; process-local reservations are not observable. Never run the `run` drain; the operator issues it. Keep counters out of durable artifacts.
